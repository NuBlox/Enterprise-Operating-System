## Purpose

Provide the formal control by which a defined requirements baseline may later be accepted as sufficiently complete and stable for the next stage. This document does not imply that requirements become immutable after sign-off; changes remain subject to controlled change and traceability.

## Current sign-off status

> **NOT READY FOR SIGN-OFF — requirements remain Draft/Candidate.**

The current requirement estate is useful for structured discovery and architecture preparation, but material evidence and decisions are still outstanding.

## Baseline proposed for eventual sign-off

The controlled requirements baseline is expected to include, at minimum:

- Business Requirements Document;
- Stakeholder Requirements Specification;
- Software Requirements Specification;
- Functional Requirements Specification;
- Non-functional Requirements Specification;
- Business Rules;
- Data Requirements and Data Dictionary;
- Interface/Integration/API Requirements;
- Reporting/Analytics Requirements;
- Acceptance Criteria;
- Requirements Traceability Matrix;
- Requirements Prioritisation;
- Business Glossary;
- relevant validated use cases/journeys/process/BPMN artifacts;
- controlled backlog and DoR/DoD.

## Sign-off readiness criteria

| Gate | Current status | Evidence required |
|---|---|---|
| Product/customer problem sufficiently validated | Not ready | Representative primary customer/user evidence |
| Initial target workflow(s) selected | Not ready | Approved outcome/workflow scope |
| BR/SR baseline validated | Not ready | Customer/business-owner validation and sources |
| Functional requirements complete enough for selected scope | Partial | Gaps/conflicts resolved for selected workflow |
| NFR quantitative targets baselined | Not ready | Availability, performance, recovery, scale, retention, accessibility and support targets |
| Business rules validated | Partial | Business/domain owners and legal/control review as applicable |
| Data authority/history/migration needs understood | Partial | Approved data semantics and source boundaries |
| Initial interfaces/system boundaries selected | Not ready | Named approved integration/interface scope |
| Acceptance criteria measurable | Partial | Workflow/NFR/customer outcome thresholds |
| RTM complete for baseline scope | Partial | Approved requirement and verification links |
| Priority/defer/reject decisions made | Partial | Product governance approval |
| Major requirement conflicts resolved | Not ready | Decision records |
| Security/privacy/compliance review completed | Not ready | Applicable review/evidence |
| Customer/pilot acceptance approach agreed | Not ready | Pilot sponsor and measurable criteria |

## Sign-off authorities to establish

The eventual baseline should identify named accountable authorities for at least:

- business/product requirements;
- technical/architecture feasibility;
- security/privacy/compliance requirements;
- quality/verification approach;
- customer/pilot requirements where a customer-specific baseline is involved.

No placeholder role in this Draft constitutes approval.

## Sign-off statement template

When the baseline is ready, approvers should confirm that:

1. the requirements are sufficient for the stated scope/stage;
2. known assumptions, exclusions and TBDs are explicit;
3. conflicts and significant risks have owners/dispositions;
4. acceptance/verification routes exist;
5. requirements may change only through controlled change/traceability;
6. approval authorises the next stated stage, not unlimited implementation scope.

## Current decision

Continue requirements discovery, customer validation and supporting analysis. Do **not** represent the current Draft requirement set as an approved solution baseline.
